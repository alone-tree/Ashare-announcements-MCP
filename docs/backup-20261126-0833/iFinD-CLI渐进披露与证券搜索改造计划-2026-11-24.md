# iFinD CLI渐进披露与证券搜索改造计划（2026-11-24）

## 一、为什么要改

用子代理实测CLI取MiniMax、智谱的收盘价和总市值，数据取对了，但暴露两个缺口：

一、AI知道help命令，却仍然绕过现成场景、自己用 `run` 拼公式，踩了两个坑：港股传五位代码返回错值（不报错）、用会前推的收盘价公式判交易日导致周末混进假数据。说明当前help只回答「有什么」，没回答「该用哪个、别踩哪个」。

二、CLI没有任何按公司名查证券代码的能力。AI只能靠网络搜索拿代码，而网络给的是五位港股代码，iFinD不认，必须再转换。这是这次测试里最实质的缺口。

用户定的方向（2026-11-24）：

- 渐进披露：多数内容放在工具返回的help里，工具描述保持极简，用到哪个查哪个。
- 要一个相对可靠的证券代码查询：输入「腾讯」至少返回「腾讯控股，0700.HK」这类主股票，代码必须是iFinD可识别的。
- 不搞太多纠错机制，除非常见且固定；让AI行动前就拿到清晰信息。

## 二、改动一：渐进披露（help返回值补导航）

不动任何取数逻辑，只改 `help.py` 返回结构，工具描述不动。

在 `overview()` 的返回值里加一个 `start_here` 导航段，按「你要什么」直接指到该调哪个命令：

| 需求 | 该调什么 |
|---|---|
| 不知道某公司代码 | `search` 命令查代码 |
| 一段区间的行情、估值 | `fetch_scene` 历史行情/估值快照 |
| 财报三表 | `fetch_scene` 对应报表场景 |
| 公司资料、股东 | `fetch_scene` 工商信息/十大股东 |
| 指数成分股 | `fetch_scene` 指数成分股 |
| 库里没有的指标 | `lookup` 查公式，再 `run` |

同时明确写出两条硬规则（这次踩坑的直接结论）：

- 优先用 `fetch_scene`，只有场景确实没有要的指标才用 `run` 自己拼公式。
- `fetch_scene` 传 `code` 前先确认代码是iFinD格式：港股四位（0700.HK），不是五位。

`scene_params()` 在历史行情场景带上关键口径：默认前复权108、剔除非交易日但保留停牌日、判据是不前推收盘价大于0。让AI看场景时就知道，不必自己猜判交易日的方法。

辅助入口 `help` 加一句：想按需求找命令先看 `start_here`。`usage.md` 同步补上 `search` 命令和新导航的说明。

## 三、改动二：内置证券代码查询

新增 `search` 命令，入口 `{"cmd":"search","keyword":"腾讯"}`。

按对象类型分通道（用户2026-11-24补充要求）：

- 股票：走东方财富证券搜索接口（`https://searchapi.eastmoney.com/api/suggest/get`），免费即时，与 `market_data_mcp/security_search.py` 同一接口。CLI保持与market-data零import依赖，请求和转换逻辑在CLI内自带一份。
- 指数：查本地 `formula_library/常用指数基本信息.csv`，按证券名称/证券代码匹配。表里代码本身就是iFinD格式（如 `000300.SH`、`000688.SH`），直接使用。
- 外汇：查本地 `formula_library/汇率代码表.csv`，按证券名称/证券代码匹配，代码本身是iFinD格式（如 `USDCNY.IN`、`USDHKD.FX`）。

三通道结果合并返回，每条带 `kind` 字段（股票/指数/外汇）标明来源。以后要支持别的类型（如板块、其他资产）按同样方式加通道即可。

为什么指数、外汇不直接走东财（2026-11-24逐条实测常用指数表38条）：

- 东财能精确命中的只有16条，另22条查不到：所有全收益指数（各种R、全收益后缀）、全部商品指数（申万商品、南华商品、易盛能化A、上期有色金属、豆粕价格）、多数境外指数（纳斯达克100、德国DAX、纳指总收益等）都查不到。
- 即便命中，东财也不给iFinD后缀：东财返回裸码`H30269`，iFinD要`H30269.CSI`；东财`SPX`，iFinD要`SPX.GI`。后缀仍需查表或猜，违背"不搞太多纠错机制"。
- 外汇同样对不上：搜「美元人民币」东财返回离岸USDCNH、中间价USDCNYC及一堆人民币期货，没有iFinD要的`USDCNY.IN`、`HKDCNY.FX`。
- 能不能从东财字段推后缀（2026-11-24多轮实测）：单靠东财不可靠。硬反例：中证全指000985（iFinD为.CSI）与沪深300 000300（iFinD为.SH）在东财字段完全一样（JYS=1、MktNum=1、TypeUS=1、SecurityType=5），无法区分。东财详情接口、其他type值都不带发布机构信息。
- 找外援的尝试：中证指数官网 `https://www.csindex.com.cn/csindex-home/indexInfo/index-basic-info/{code}` 返回 `publishChannelCn` 字段，发布渠道=卫星→iFinD后缀.SH，=指数通→.CSI。16条SH/CSI指数上验证，能判的9条全对0错，解决了东财那个反例。但7条全收益/特殊指数渠道为"数据服务平台"判不了，且该接口连续请求会被限流。引入它作为常规依赖会增加外部接口和限流风险，违背"免费+及时、不等待"。
- 结论：股票走东财（命中率高、清洗后代码可用）；指数、外汇走本地表（代码本身是iFinD格式，零转换、零猜测、零外部依赖）。三通道各司其职。索引查询以本地表完整代码为准；本地表没有的冷门指数，东财找到候选但后缀无法确定时明确提示用户，不自己猜。中证官网的发布渠道规律仅作为未来扩展冷门指数的备选思路，不进常规方案。

### 代码转换规则（iFinD可识别）

按 `market_data_mcp/routing.py` 的 `to_ifind` 既有实测规则：

- 港股：五位裸码去前导零后补足四位，`00700`→`0700.HK`。这是本次踩坑的核心，必须做对。
- A股/北交所：原样带后缀，如 `600519.SH`、`920002.BJ`、`000001.SZ`。
- 美股：字母代码加 `.US`（如 `AAPL.US`）；美股后缀细化（.O/.N）由iFinD侧探测，搜索结果先给 `.US` 并标注。

筛选与排序（为了行动前就清晰，不是事后纠错）：

- 只返回能转成iFinD代码的证券，转成空的（指数、板块、票据、权证）不进主结果。
- 正股优先：港股 `type_us=3` 是正股，`type_us=6` 是权证/R股/衍生品，正股排在前面。
- 名称匹配的排前，例如输入「腾讯」，`腾讯控股 0700.HK` 必须第一条。
- 每条结果带 `ifind_code` 字段，AI可直接复制到 `fetch_scene`/`run`，不用自己转换。
- 结果顶部带一句提示：代码可直接用于CLI取数；搜索命中不代表与查询词是同一家公司，名称相近 please 自行核对。

### 返回结构（草案）

```
{
  "ok": true,
  "keyword": "沪深300",
  "note": "ifind_code可直接传给CLI取数；名称相近请核对是同一标的",
  "matches": [
    {"name":"沪深300","ifind_code":"000300.SH","kind":"指数","full_name":"沪深300指数"},
    {"name":"300收益","ifind_code":"H00300.CSI","kind":"指数","full_name":"沪深300全收益指数"}
  ],
  "excluded": []
}
```

股票结果 `kind` 为「股票」，另带 `market`（港股/A股/美股）、`type`（正股）。「腾讯控股-R」「腾讯法兴七三购A」这类R股/权证不进matches，放 `excluded` 段并注明类型，不干扰主选择。

## 四、验证

改完实测以下样本，确认返回和取数都能跑通：

- 腾讯：股票通道第一条必须是「腾讯控股 0700.HK」（四位）；权证/R股进excluded。
- 贵州茅台：返回「贵州茅台 600519.SH」。
- MiniMax、智谱：返回四位港股代码，与上一轮实测的 `0100.HK`/`2513.HK` 一致。
- 沪深300：指数通道返回「沪深300 000300.SH」。
- 美元人民币：外汇通道返回「美元人民币 USDCNY.IN」或对应常用条目。
- 拿搜索返回的 `ifind_code` 直接跑一次 `fetch_scene`，确认能取到数（验证代码格式对iFinD可用）。

## 五、不改的部分

- 不改取数公式、场景清单、engine.py。
- 不加复杂的输入校验纠错；只在help里把正确用法前置说明。
- 不查catalog.jsonl。
- 不动market-data（即将退役），仅在CLI内自带必要的搜索与转换逻辑。
